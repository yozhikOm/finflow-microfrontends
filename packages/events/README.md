# @yozhikom/finflow-events

События об изменениях между приложениями FinFlow (ADR-0006). Через пакет одно приложение узнаёт, что у соседа изменились данные. Событие приходит в ту же вкладку и в соседние: в основе `BroadcastChannel`.

## Пример

```ts
import { publish, subscribe } from '@yozhikom/finflow-events';

// transactions после успешной мутации
publish('transactions-changed');

// accounts на странице со списком счетов
useEffect(
  () => subscribe(['transactions-changed'], () => refetch()),
  [refetch],
);
```

## События

| Событие                | Владелец       | Кто слушает             |
| ---------------------- | -------------- | ----------------------- |
| `transactions-changed` | `transactions` | `accounts`, `analytics` |
| `categories-changed`   | `transactions` | `analytics`             |
| `accounts-changed`     | `accounts`     | —                       |

Событие — факт об изменении сущностей владельца, а не команда. Полезной нагрузки у него нет: что перезапросить, решает получатель. Шлёт событие только владелец сущностей. Список по владельцам экспортируется как `eventsByOwner`, имя канала — как `CHANNEL`.

`publish(event)` отправляет событие всем подписчикам на него: в этой вкладке и в соседних. `subscribe(events, listener)` вызывает `listener` с типом события на каждое событие из `events`. Возвращает отписку, которая закрывает канал. Её вызывают при размонтировании, удобно вернуть её прямо из `useEffect`.

Сообщения неизвестного типа подписчик молча пропускает: их могла прислать более новая версия пакета в соседнем приложении. Пропущенное событие ничего не ломает. Страница при монтировании и так запрашивает данные с сервера, а события нужны только тому, что уже на экране.

## Совместимость версий

Каждое приложение включает в свою сборку свою версию пакета. Поэтому разные версии должны понимать сообщения друг друга.

В `fixtures/messages.json` лежат «золотые» сообщения: их слала в канал текущая версия или одна из прошлых. Тесты проверяют, что текущая версия принимает каждое из них и что на каждый тип события есть хотя бы одна фикстура.

Удалять или менять фикстуру можно только в мажорной версии. CI берёт фикстуры последнего тега `events-v*` и смотрит, какие из них удаляет или меняет сам PR. Если такие есть, а в заголовке PR нет `!`, проверка падает. Ломающее изменение, которое уже влито в `develop`, следующим PR в вину не ставится.

## Какая версия нужна

- Новое событие — `feat`, минорная версия.
- Переименование или удаление события, смена имени канала или формы сообщения — `feat!`, мажорная версия. Такое изменение выкатывают по шагам ADR-0011: на переходе отправитель шлёт и старое, и новое событие.

## Первый выпуск

Пакет публикуется из workflow `release-please.yml` через trusted publishing, без `NPM_TOKEN` (ADR-0013). Trusted publisher на npmjs.com можно настроить только у пакета, который уже есть в реестре. Поэтому версию `1.0.0` публикуют один раз вручную:

1. Влить release PR пакета. Release-please создаст тег `events-v1.0.0`. Job `publish` упадёт с ошибкой «ещё нет на npmjs»: так и должно быть.
2. Собрать и опубликовать сборку тега:

   ```sh
   git checkout events-v1.0.0
   cd packages/events
   npm ci && npm run typecheck && npm test && npm run build
   npm publish --access public
   ```

3. На npmjs.com в настройках пакета добавить trusted publisher: GitHub Actions, репозиторий `yozhikOm/finflow-microfrontends`, workflow `release-please.yml`. Имя файла должно совпадать точно.

Перезапускать упавший job не нужно: версия `1.0.0` уже опубликована. Следующие версии публикует workflow.
