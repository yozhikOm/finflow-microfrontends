# Границы микрофронтендов: категории внутри transactions, счета отдельно

`shell` — хост. Remote-приложения: `transactions` (транзакции и категории), `accounts` (счета и балансы), позже `analytics` (отчёты). Категории не существуют без транзакций, поэтому живут в одном микрофронтенде с ними. Отдельный remote для справочника категорий был бы лишней границей. Счета вынесены отдельно: это самостоятельная сущность со своим жизненным циклом и балансом. Бэкенд у всех один (`server`, модули за одной GraphQL-схемой): отдельные бэкенды по микрофронтендам — это уже микросервисы, вне учебной цели проекта.

## Consequences

- Выбор счёта в `transactions` — это компонент `AccountPicker`, который экспортирует `accounts` через Module Federation. `transactions` подключает его как remote, а не рисует свой список. Всё отображение счетов остаётся у их владельца, но `transactions` в рантайме зависит от того, доступен ли `accounts`, и обязан сделать запасной вариант на случай недоступности.
- Контракт `AccountPicker` узкий: props `value: accountId | null`, `onChange(accountId)` и необязательный фильтр `currency`. Счета компонент загружает из GraphQL сам, через границу передаётся только id. Так `accounts` может свободно меняться внутри.
- Если `accounts` не загрузился, `transactions` ловит ошибку в error boundary, показывает «Счета временно недоступны» и блокирует ввод новой транзакции, а список транзакций продолжает работать. Своего запасного списка счетов у `transactions` нет: иначе знания о счетах снова оказались бы в двух местах.

## Considered Options

- Отдельный микрофронтенд `categories`: отвергнут, справочник без транзакций не нужен.
- Всё в одном `transactions`: отвергнут, тогда нечему учиться в связи между микрофронтендами.
- `shell` загружает счета и передаёт их в `transactions` через props: отвергнут, `shell` начал бы знать о домене.
