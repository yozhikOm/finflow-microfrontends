# Границы проверяются против выкаченной версии, e2e — на release PR

Staging нет (ADR-0009), поэтому до выпуска каждая граница между приложениями проверяется с обеих сторон, причём вторая сторона берётся в той версии, что работает в проде. Для `@mf-types` это production-адрес производителя (ADR-0009), для всего, что лежит в репозитории (схема `server`, код потребителей), — последний тег release-please этого приложения: в прод уходит только сборка тега. Сравнение с `master` проверяло бы состав, которого в проде нет: поле схемы, которое уже в `master`, но ещё не выпущено, сломало бы прод при зелёном CI. e2e идёт по прод-подобному составу на release PR, у которого ровно одно приложение: оно берётся из PR, остальные — с тегов.

## Consequences

- После ручного отката, до следующего выпуска, последний тег не совпадает с продом, и проверки смотрят не на то. Это принято.
- Инструменты: Vitest, React Testing Library и MSW во всех приложениях и пакетах, Playwright для e2e. GraphQL подменяется на уровне сети: экспорт оборачивает себя в свой `ApolloProvider` (ADR-0006), и `MockedProvider` снаружи до него не дотянется.
- Поведение экспорта Module Federation (для `AccountPicker` — ADR-0001) проверяют контрактные тесты производителя: они монтируют модуль из `exposes` через публичные props. Удалённый или изменённый контрактный тест виден в diff как ломающее изменение (ADR-0011). Потребитель тестирует свою сторону с заглушкой вместо remote-модуля.
- CI производителя проверяет выкаченных потребителей против нового контракта: GraphQL-операции каждого фронтенда на его последнем теге валидируются против новой `schema.graphql`, а потребители экспортов на последних тегах прогоняют `tsc` против свежих `@mf-types`. Проверка падает на любом изменении, ломающем выкаченного потребителя, и заменяет ручной список потребителей из ADR-0011.
- Codegen фронтенда читает `server/schema.graphql` из рабочей ветки (ADR-0002), а CI дополнительно валидирует операции против схемы с последнего тега `server-v*`. Новое поле сначала выкатывает `server`, как новый экспорт — производитель (ADR-0009).
- `routes` и `events` бандлятся каждым приложением своей версией, поэтому совместимость нужна между версиями пакета. В пакете лежат «золотые» фикстуры: адреса и сообщения, которые строили и слали прошлые версии. Текущая версия обязана разобрать каждый адрес (или ответить редиректом) и принять каждое сообщение. Фикстура удаляется только в major.
- Stories кита `ui` служат тестами взаимодействий и a11y (`@storybook/addon-vitest`). Имена токенов `theme.css` CI сверяет с последней опубликованной версией пакета (ADR-0005). Визуальной регрессии нет.
- Логику обёртки сбоя (таймаут, «Повторить», заглушка, ошибка рендера) проверяют тесты пакета `remote` с подложным загрузчиком и поддельными таймерами. e2e проверяет только то, что делает настоящий рантайм Module Federation: старт `shell` при недоступном манифесте (`loaded-first`), повторы `retry-plugin`, 404 для пропавшего чанка, тексты сбоя (ADR-0010) и синхронизацию двух вкладок через `BroadcastChannel`.
- e2e лежит в корне в `e2e/`. У каждого прогона чистая MongoDB сервисом CI и `server` с тега, данные каждый тест создаёт сам через GraphQL, общего seed нет.
- После деплоя один smoke-сценарий из `e2e/` только на чтение идёт против прода с таймаутом около двух минут: `server` просыпается. Упавший smoke делает workflow красным, откат запускается вручную (ADR-0009).
- У каждого приложения свой release PR (`separate-pull-requests`), и мержатся они по очереди, сначала производитель. В общем release PR потребитель нового экспорта выкатывался бы одновременно с производителем, а его typecheck против прод-`@mf-types` был бы красным.
- В `master` напрямую не коммитят. Рабочая ветка вливается в `develop` squash-ом, commitlint проверяет заголовок PR. `develop` вливается в `master` только merge commit: при squash release-please потерял бы типы коммитов и их привязку к приложениям. Срочное исправление и revert после отката идут из `hotfix/*` от `master` прямо в `master`.
- После каждого push в `master` workflow вливает `master` в `develop`, чтобы версии и `CHANGELOG.md` от release-please не расходились. При конфликте он открывает PR.
- Быстрые проверки (lint, typecheck, build, unit и контрактные тесты, проверки против выкаченной версии) обязательны в PR в `develop` и в `master`. e2e идёт на release PR и вручную. PR `develop` → `master` e2e не гоняет: в нём несколько приложений, а в прод они уходят по одному.

## Considered Options

- Consumer-driven контракты в духе Pact: для трёх экспортов и одного автора тяжеловесно.
- Ручная проверка потребителей в описании PR (ADR-0011): её легко забыть, а репозиторий с тегами позволяет её автоматизировать.
- Codegen от схемы с тега `server-v*`: новое поле нельзя было бы использовать даже локально до выпуска `server`.
- e2e по сборке всего `master`: проверяет состав, которого в проде не будет. e2e только против прода: падает уже после выката, а `server` засыпает.
- Общий seed-скрипт для e2e: ещё один контракт со схемой, который тоже надо проверять.
- Визуальная регрессия скриншотами: эталоны пришлось бы снимать в Docker из-за шрифтов, Chromatic платный, а к теме микрофронтендов это не относится.
- Автооткат по упавшему smoke: smoke может упасть из-за сна `server`, а сам механизм пришлось бы тестировать.
- Коммиты прямо в `master` с общим release PR: до прода код не проходит ни одних ворот, кроме release PR, а порядок «сначала производитель» внутри одного PR невыполним.
