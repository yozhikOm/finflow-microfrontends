# Сбой remote-модуля: `loaded-first`, повторы, диагностика в хуке, интерфейс в своей обёртке

Потребители (`shell`, `transactions`) загружают remote-приложения с `shareStrategy: 'loaded-first'`, повторяют сетевые сбои через `@module-federation/retry-plugin`, а что увидит пользователь, решает обёртка в месте использования: `lazy`, `Suspense`, `ErrorBoundary`, таймаут и «Повторить». Runtime-хук `errorLoadRemote` только пишет диагностику. По умолчанию (`version-first`) хост на старте запрашивает манифесты всех remote-приложений, и одно недоступное ломает всю страницу. А текст сбоя зависит от места («Счета временно недоступны» блокирует ввод транзакции), о котором хук ничего не знает.

## Consequences

- При `loaded-first` синглтоны `shared` берутся из того, что загрузилось первым, то есть из `shell`. Remote-приложение на более свежей минорной версии `react-router` молча получит версию `shell` и упадёт, если пользуется новым API. Поэтому обновление `shared`-пакета (`react`, `react-dom`, `react-router`) сначала выкатывается в `shell`, затем в remote-приложения.
- `retry-plugin`: два повтора с короткой паузой, без запасных доменов, ведь домен у приложения один (ADR-0009).
- `errorLoadRemote` пишет в консоль remote-приложение, модуль и код ошибки и ничего не возвращает, поэтому исходная ошибка доходит до `ErrorBoundary`. Стадию сбоя (манифест, entry, модуль) определяет код ошибки (`RUNTIME-003`, `RUNTIME-013`…), а не `args.lifecycle`: при `loadRemote` хук всегда получает `onLoad`. Любое truthy-значение, в том числе `args` из примера в блоге Module Federation, подставится вместо модуля.
- Диагностика пишется только в консоль браузера, сервиса мониторинга нет.
- Обёртка и runtime-плагин с `retry-plugin` и `errorLoadRemote` лежат в npm-пакете `@yozhikom/finflow-remote`. Как `events` (ADR-0006) и `routes` (ADR-0008), каждое приложение бандлит его своей версией вне `shared`. О домене пакет не знает: тексты сбоев передаёт потребитель.
- Пока модуль грузится, на его месте стоит заглушка его формы без текста: неактивное поле у `AccountPicker`, серая полоса у метки счёта, пустая область под шапкой `shell` у раздела. Загрузка дольше 10 секунд, с учётом повторов, считается сбоем.
- Сбой загрузки и ошибка рендера загруженного модуля выглядят для пользователя одинаково. Различие видно только в консоли.
- `AccountPicker`: «Счета временно недоступны» с кнопкой «Повторить», ввод новой транзакции заблокирован, список работает (ADR-0001). Метка счёта: приглушённое «—» с подсказкой «Счета временно недоступны», без кнопки. Раздел целиком: маршрутный `ErrorBoundary` в `shell` (ADR-0008).
- «Повторить» работает без перезагрузки страницы: Module Federation не кэширует неудачную загрузку `remoteEntry` или манифеста, а отклонённый промис кэширует сам `React.lazy`, поэтому повтор создаёт новый `lazy`. Если и так не срабатывает, страница перезагружается.
- Недоступный `server` — сбой данных, а не кода. Его обрабатывает владелец компонента через Apollo, и это решение его не касается.

## Considered Options

- `version-first` с обработкой стадии `beforeLoadShare` в `errorLoadRemote`: самая свежая версия `shared` побеждает, порядок выката не важен. Но то, что запуск после этого продолжится, не проверено, и `shell` при каждом старте запрашивал бы манифесты всех remote-приложений.
- `createLazyComponent` из `@module-federation/bridge-react`: готовый `fallback({ error, errorType })`, но тянет пакет, который сам подменяет `react-router` (ADR-0007).
- Запасной компонент из `errorLoadRemote`: хук не знает, где компонент стоит и что должен увидеть пользователь.
- Обёртка в ките `ui`: кит — визуальные компоненты без знания о Module Federation (ADR-0005). Копия в каждом потребителе: поведение при сбое разойдётся.
