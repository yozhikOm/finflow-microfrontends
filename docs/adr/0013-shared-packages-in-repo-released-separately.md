# Общие npm-пакеты живут в этом репозитории и выпускаются каждый своим релизом

Пакеты `ui`, `events`, `routes` и `remote` (ADR-0005, ADR-0006, ADR-0008, ADR-0010) лежат в `packages/<имя>/` рядом с приложениями. Каждый из них — независимый npm-пакет со своим lockfile и отдельный компонент release-please: свои теги `<имя>-vX.Y.Z`, свой `CHANGELOG.md`, свой release PR. Выпущенную версию публикует на npmjs workflow release-please со сборки тега, через trusted publishing и без токена npm. Приложение переходит на новую версию пакета через PR Dependabot. Отдельные репозитории дали бы четыре CI, четыре конфига release-please и четыре набора секретов для одного автора. Кроме того, проверки ADR-0012 потеряли бы теги приложений и пакетов в одной истории.

## Consequences

- Workspaces нет. Workspace подставил бы локальный пакет вместо опубликованной версии, а это та же зависимость `file:`, которую отверг ADR-0005.
- Scope коммита — приложение или пакет: `feat(ui): …`. Release-please, как и для приложений, относит коммит к пакету по путям, поэтому коммит не выходит за пределы одного пакета.
- Все пакеты стартуют с `1.0.0`, а не с `0.x`. При `bump-minor-pre-major` коммит `feat!` до 1.0 поднимал бы только minor, а правила ADR-0005, ADR-0006, ADR-0008 и ADR-0012 («переименование — major», «фикстура удаляется только в major») сформулированы для major.
- Публикация: `npm publish --provenance --access public` при выпуске пакета, с правом `id-token: write` и npm не ниже 11.5.1. Отложенного trusted publisher в npm нет, поэтому первая версия каждого пакета один раз публикуется вручную, после чего на npmjs.com настраивается trusted publisher. Имя файла workflow там должно совпадать точно.
- Публикуется только сборка тега, поэтому последний тег пакета и его последняя опубликованная версия совпадают. Проверки берут прошлую версию пакета из тега `<пакет>-v*`, как всё остальное в ADR-0012.
- `ui` публикуется исходниками (ADR-0005). `events`, `routes` и `remote` собираются `tsc` в `dist` с `.d.ts`: в исходниках `tsc` потребителя проверял бы код пакета по своим настройкам, ведь `skipLibCheck` касается только `.d.ts`.
- Пакеты друг от друга не зависят. Заглушку загрузки и рендер сбоя с колбэком `retry` обёртка в `remote` получает от потребителя, так же как тексты (ADR-0010). Если бы `remote` импортировал `ui`, в приложении оказались бы два кита с разными классами. React — `peerDependency` у пакетов, которым он нужен.
- Dependabot следит за каталогами приложений и разрешает только `@yozhikom/finflow-*`. PR он открывает в `develop` с префиксом `fix(<приложение>)`, потому что `chore` и `build` не выкатываются (ADR-0009), а переход потребителя — `fix` (ADR-0011). Если вместе с обновлением приложение начинает пользоваться новой возможностью пакета, коммит пишет человек и выбирает тип по смыслу.
- Версии наших пакетов в `package.json` приложений пишутся точно (`1.3.0`), поэтому версия кита, забандленная в приложение, видна прямо в `package.json` и его диффе.
- Изменение пакета и его использование в приложении доходят до прода по порядку: выпуск пакета → публикация → PR с обновлением в приложении → выпуск приложения. До публикации изменение примеряют через `npm pack` и `npm install <путь к .tgz> --no-save`. `npm link` не годится: React резолвился бы из `node_modules` пакета, и на странице оказались бы две копии.
- Сужение контракта пакета требует `!` в заголовке PR. Для этого CI сравнивает пакет с его последним тегом: удаление или переименование токена `theme.css` или удаление и изменение «золотой» фикстуры `routes`/`events` без `!` даёт красный CI. Проверка идёт в PR в `develop` и `hotfix/*` → `master`, где заголовок PR — будущий коммит. Фикстуры пишутся руками, а тест требует хотя бы одну фикстуру на каждый публичный адрес и тип события.
- Тему на странице подключает только `shell` (ADR-0005), поэтому CI remote-приложения проверяет: каждое `var(--…)` из CSS приложения и CSS его версии `ui` должно быть объявлено в `theme.css` той версии `ui`, что стоит у `shell` на последнем теге `shell-v*`. Новый токен сначала выкатывает `shell`, как новый экспорт — производитель (ADR-0009). Dependabot открывает PR во все приложения сразу, порядок за него держит эта проверка.
- Пакеты входят в матрицу CI: typecheck, тесты, а для трёх пакетов ещё сборка `dist`. Витрина Storybook кита — отдельный проект Cloudflare Pages, на который при выпуске `ui` уходит сборка тега, как у приложений (ADR-0009).

## Considered Options

- Отдельный репозиторий на каждый пакет: четыре CI и конфига release-please, а тег пакета и тег приложения оказались бы в разных историях.
- npm workspaces в корне: приложения получали бы локальный пакет вместо опубликованной версии (ADR-0005).
- Старт с `0.x`: правила major из прошлых ADR не работали бы, а `^0.2.0` не принимает `0.3.0`.
- Гранулярный `NPM_TOKEN` в secrets: долгоживущий секрет, который надо продлевать. Публикация вручную: версия на npm могла бы разойтись с тегом.
- Renovate: гибче Dependabot, но это ещё одно GitHub App и ещё один конфиг. Обновление вручную: легко забыть, и `shell` надолго останется на старом `theme.css`.
- Диапазон `^1.3.0` с версией в lockfile: какой кит забандлен, видно только из lockfile.
- `events`, `routes` и `remote` исходниками, как `ui`: у них нет CSS Modules, ради которых ADR-0005 отказался от сборки.
- `ui` как `peerDependency` у `remote`: версии кита и обёртки связали бы друг друга.
- Прошлая версия пакета из npm (`npm pack …@latest`): по содержимому то же, что тег, но проверке нужна сеть.
