# Доменный отказ: один код `RULE_VIOLATION`, правило из enum схемы, текст у клиента

Когда ввод нарушает доменное правило («сумма должна быть больше нуля», «счёт зачисления обязателен для перевода», «имя счёта уже занято»), `server` не бросает обычный `Error`, а отвечает ошибкой GraphQL с `extensions: { code: 'RULE_VIOLATION', rule, field? }`. Это отказ, а не сбой данных (ADR-0014): клиент отличает его одним сравнением `code`. Значения `rule` объявлены в схеме как `enum RuleViolation` и входят в контракт `server`. Текст для пользователя по-русски пишет приложение, которому принадлежит форма, по значению `rule`. `message` от `server` остаётся английским, он для консоли и разработчика.

## Consequences

- `rule` — значение `enum RuleViolation` из SDL. Ни одно поле его не возвращает, enum нужен, чтобы codegen (ADR-0002) дал клиентам union-тип, а сверка схемы в CI (ADR-0012) видела удалённое значение. Новое правило — расширение, `feat`. Удаление или переименование значения — сужение по ADR-0011, `feat!` после перехода потребителей.
- Каталог MVP. Транзакция: `AMOUNT_NOT_POSITIVE`, `CURRENCY_MISMATCH` (валюта суммы не совпадает с валютой счёта, у перевода — сумма зачисления со счётом зачисления), `DATE_IN_FUTURE`, `CATEGORY_REQUIRED`, `CATEGORY_TYPE_MISMATCH`, `CATEGORY_NOT_ALLOWED`, `TARGET_ACCOUNT_REQUIRED`, `TARGET_ACCOUNT_NOT_ALLOWED`, `SAME_ACCOUNT`, `ACCOUNT_ARCHIVED`, `CATEGORY_ARCHIVED`, `TYPE_IMMUTABLE`. Счёт: `ACCOUNT_NAME_TAKEN`, `CURRENCY_IMMUTABLE`, `ACCOUNT_HAS_TRANSACTIONS`. Категория: `CATEGORY_NAME_TAKEN`, `CATEGORY_HAS_TRANSACTIONS`. Общее: `NOT_FOUND`.
- `field` необязателен. Это имя поля input-типа схемы (`amount`, `targetAccountId`, `name`). Если правило касается двух полей, указывается то, которое пользователь скорее поменяет: у `SAME_ACCOUNT` это `targetAccountId`.
- Приходит одно нарушение — первое по порядку проверки. Списка нарушений нет: простые правила форма проверяет сама, до `server` обычно доходит одно, зависящее от данных.
- Отказом не считаются ошибки самого клиента: запрос не подходит под схему (в том числе собственный `BAD_USER_INPUT` Apollo), ссылка по id на несуществующий счёт или категорию. Это сбой по ADR-0014.
- Удаление идемпотентно: удалить то, чего уже нет, — успех, строка исчезает, событие уходит как обычно. `NOT_FOUND` бывает только у правки: форма говорит «Запись уже удалена» и закрывается.
- Вид транзакции и валюта счёта не меняются (`GLOSSARY.md`). `UpdateTransactionInput` пока принимает `type` и отказывает с `TYPE_IMMUTABLE`, если он отличается от текущего. Убрать поле из input — отдельный шаг «сузить» по ADR-0011.
- Форма заранее проверяет то, что видно по её собственному вводу: обязательные поля, сумма больше нуля, дата не позже сегодня, разные счета у перевода. Ошибка показывается у поля сразу, кнопка не блокируется. Правила, которым нужны чужие данные (имя занято, архив, есть транзакции), проверяет только `server`. Он главный, проверки в форме — копия для удобства, общего пакета правил нет.
- Где виден отказ. Если `field` есть в форме, текст стоит под полем, поле подсвечено, фокус переходит на него. Иначе текст стоит у кнопки, там же, где «Не удалось сохранить» из ADR-0014, но без «Повторить». Отказ действия из строки списка — компактный `ErrorState` в строке с подсказкой («По счёту есть транзакции — его можно архивировать»). Новых компонентов в `ui` не нужно.
- Тексты живут в приложении-владельце формы, не в `ui` и не в общих пакетах. Для незнакомого `rule` (сервер уже выкатил новое правило, клиент ещё нет) — общий текст «Сохранить не получилось: проверьте введённые данные». Это по-прежнему отказ, без «Повторить».
- В настройке `ApolloClient` каждого приложения (ADR-0014) есть `isRuleViolation(error)` → `{ rule, field } | null`. `onError`-link пропускает отказ молча и пишет в консоль только сбои.
- У `server` на каждое значение `enum RuleViolation` есть тест поведения: ввод → `code`, `rule`, `field` (ADR-0012). Тесты перебирают значения enum, поэтому правило без теста роняет CI. Потребители проверяют только свои тексты по кодам.

## Considered Options

- Свой `extensions.code` на каждое правило: чтобы отличить отказ от сбоя, клиенту нужен полный список, а новое правило до обновления клиента выглядело бы сбоем.
- Стандартный `BAD_USER_INPUT`: его же Apollo отдаёт, когда переменные не подходят под схему, а это ошибка клиента, то есть сбой.
- Ошибки как данные (union `CreateTransactionResult` с типами ошибок): каждая мутация получила бы payload-обёртку, а ADR-0014 уже разделил отказ и сбой по `extensions.code`.
- Список правил только в документации: удаление правила ничем бы не проверялось.
- Текст с `server`: русский текст на сервере связывает формулировки всех форм с выпусками `server`, а поле, к которому он относится, всё равно нужно отдельно.
- Общий пакет правил для формы и `server`: ещё одна связь выпусков ради пяти тривиальных проверок.
